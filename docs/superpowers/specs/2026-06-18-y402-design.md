# y402 — Design Spec

- **Date:** 2026-06-18
- **Status:** Approved design, pre-implementation
- **Owner:** Ivan Anishchuk

## Summary

`y402` is a minimal, self-custodial command-line USDC wallet that quietly speaks
the [x402](https://www.x402.org/) payment protocol on behalf of a local AI agent
(initially Claude). You `init` it once, `topup` a couple of dollars by scanning a
terminal QR code, and from then on it transparently handles `402 Payment Required`
responses within safety caps. **The wallet is the product; x402 is just the
dialect it speaks.**

The first deliverable is a CLI plus a thin Claude *skill* wrapper, usable locally
with no third party in the payment path.

## Goals

- A simple, self-custodial hot wallet holding a small USDC balance.
- Transparent x402 payment on the **buyer side** with no middleman the buyer
  controls or pays: sign locally, hand the signed authorization to the counterparty.
- Safety by default: tiered confirm/refuse policy with hard caps and an audit log;
  an `unattended` mode for fully automated agent use.
- Multi-chain by design (EVM), starting on Base Sepolia testnet.
- Low operational friction on local desktop Linux / macOS.
- A clean wallet core (`eth-account`-led) that can grow other wallet operations
  later — x402 is one consumer of it, not the whole of it.

## Non-goals (explicitly out of scope for v1)

- **Self-settlement / broadcasting transactions / holding ETH for gas.** v1 uses
  the gasless local-signing path only. Self-settle is *dropped*, not deferred —
  it would re-introduce a dependency (RPC + gas) and works against the
  no-middleman, gasless ethos.
- **Hardened headless/server key storage.** Subject to later research; v1 targets
  local desktop with the OS keyring plus a minimal encrypted-file fallback.
- **Non-EVM chains (Solana, etc.).** Different key type; future backend behind the
  same registry seam.
- **MCP server.** A later increment; the v1 agent integration is a Claude skill.
- **Multiple accounts / key rotation / general DeFi operations.**

## Background: x402 (grounded)

x402 is an HTTP-native payment protocol. The buyer-side flow we implement:

1. Client requests a resource; the server responds `402 Payment Required` with a
   JSON body listing `accepts[]` — one or more payment requirements, each with
   `scheme`, `network` (CAIP-2, e.g. `eip155:84532`), `asset` (token address),
   `payTo`, and `maxAmountRequired`.
2. Client picks a requirement it can satisfy and signs an **EIP-3009
   `transferWithAuthorization`** message (EIP-712 typed data) authorizing transfer
   of USDC to `payTo`. No on-chain transaction is broadcast by the buyer.
3. Client retries the request with the signed payload in the **`X-PAYMENT`**
   header. The exchange happens on the same endpoint — no redirects, no sessions.
4. The **server** verifies and settles (directly on-chain or via *its own*
   facilitator) and returns the resource.

Consequences that shape this design:

- The buyer **pays no gas** and **calls no facilitator**. The facilitator, if any,
  is the seller's infrastructure — we neither call it, pay it, nor can remove it,
  and it is invisible from our side.
- `y402 pay` needs **no RPC at all** — it is pure local signing plus the HTTP
  conversation already in progress. An RPC endpoint is needed only for read-only
  balance queries (`balance`, optional pre-pay checks) and can point at the user's
  own node.
- A local library that builds a signature on your machine (`x402`, `eth-account`)
  is **not** a middleman — no service, no money path.

Confirmed facts used by the design:

- Protocol-supported networks: Base (`eip155:8453`), Base Sepolia (`eip155:84532`),
  Polygon (`eip155:137`), Arbitrum One (`eip155:42161`), World (`eip155:480`),
  Ethereum (`eip155:1`), and Solana (future).
- USDC on Base Sepolia: `0x036CbD53842c5426634e7929541eC2318f3dcf7e`.
- Seller-side facilitators (referenced, not called by us): `https://x402.org/facilitator`
  (testnet), `https://api.cdp.coinbase.com/platform/v2/x402` (mainnet).
- USDC is an EIP-3009 token: `transferWithAuthorization` enables fully gasless
  transfers where the buyer signs off-chain and the settling party submits the tx.

## Architecture

One Python package, layered for isolation. Each module has one clear purpose and a
well-defined interface; the CLI / skill / (later) MCP are thin shims over the core.

### `wallet` — eth-account-led, the trust root

Owns the key and all signing. The private key lives here and is **never** handed to
the `x402` package.

- Key lifecycle: generate, load, address.
- Signing primitives: `sign_typed_data` (EIP-712), `sign_message`.
- Deliberately general so other wallet operations can be added later. v1 needs only
  typed-data signing for the EIP-3009 authorization.

### `keystore` — key-at-rest

- Primary: OS keyring via the `keyring` library (Secret Service / libsecret on
  desktop Linux, Keychain on macOS).
- Fallback (auto-selected when no keyring is available): a minimal encrypted JSON
  keystore (eth-account `encrypt`/`decrypt`), passphrase from `Y402_PASSPHRASE` env
  or interactive prompt.
- Never a plaintext key on disk. Hardened headless storage is parked research.

### `registry` — network definitions (the multi-chain seam)

A mapping `eip155:<id>` → `{ rpc_url, usdc_address, eip712_domain, enabled }`.
Adding a chain is adding an entry — nothing else. v1 ships **Base Sepolia enabled**,
with Base mainnet and the other EVM networks present but disabled / addable.
EVM-only in v1 (one secp256k1 key = the same address on every EVM chain).

### `x402` integration — protocol formatter we drive

Uses the official `x402` Python package for the protocol envelope: parse the `402`
`accepts[]`, shape the payment payload, and produce the EIP-712 typed-data for the
chosen scheme/network. **Our `wallet` signs that typed-data**; we then assemble the
`X-PAYMENT` header and retry. The package never holds the key and we never configure
a client-side facilitator.

### `policy` + audit

Sits between "parsed 402 offer" and "sign + retry":

- **Tiered (default):** auto-pay ≤ `auto_threshold` (`$0.01`); **confirm**
  interactively in the band up to `per_payment_cap` (`$0.10`); **refuse** above it.
  A cumulative `daily_cap` (`$1.00`) is enforced and rolls over daily.
- **`unattended`:** the confirm band flips to auto-approve; caps still hard-refuse
  above. This is the mode the skill (and later MCP) pass through, since an agent
  cannot answer a TTY prompt.
- Every decision (pay / confirm / refuse, with amount, host, network, resource) is
  appended to a JSONL **audit log** in the config directory.

All thresholds are configurable; defaults are deliberately low, and the small
top-up balance is the real backstop.

### Shims

- **`cli`** (`typer`): the v1 face — `init`, `topup`, `balance`, `pay`, `config`, `log`.
- **`skill`**: a thin Claude `SKILL.md` that shells to `y402 pay --unattended`.
- **`mcp`** (later): a thin FastMCP server exposing `fetch_with_payment` / `balance`.

## Data flow: `y402 pay <URL>`

1. Issue the HTTP request.
2. On `402`, parse `accepts[]`; keep entries whose `network` is in the registry and
   `enabled`; select one (prefer the configured default network, else lowest
   `maxAmountRequired`).
3. Run the `policy` check on the selected amount → pay / prompt / refuse.
4. If paying: ask `x402` for the EIP-3009 typed-data; have `wallet` sign it;
   assemble `X-PAYMENT`; retry the request.
5. Return the resource body; append the outcome to the audit log.

No RPC is touched on this path.

## Network registry & multi-chain

Selection is the multi-chain heart: the server's `accepts[]` is the menu, the
registry is what we can satisfy, and we pick the intersection. Because the buyer
holds one address across all EVM chains, the user funds whichever chain they like
and `y402` pays on whichever enabled network the seller will accept.

## Payment policy & safety — defaults

| Setting | Default | Meaning |
| --- | --- | --- |
| `auto_threshold` | `$0.01` | Pay silently at/under this. |
| `per_payment_cap` | `$0.10` | Confirm in the band up to here; refuse above. |
| `daily_cap` | `$1.00` | Cumulative per-day refuse ceiling. |
| `unattended` | `false` | Flip the confirm band to auto-approve. |

CLI overrides: `--unattended`, `--max <usd>`, `--network <id>`.

## CLI commands

- `y402 init` — generate key, store via keystore, print address.
- `y402 topup` — print address + a **terminal QR** (`qrcode`); tell the user to send
  USDC on a chosen network.
- `y402 balance [--network <id>]` — read-only USDC balance across enabled networks
  (uses RPC).
- `y402 pay <URL>` (alias `fetch`) — perform the request, auto-handle `402` per
  policy, return the body. Overrides as above.
- `y402 config [get|set] …` — caps, `unattended`, default network, RPC URLs.
- `y402 log` — tail the audit log.

## Claude skill integration (v1 agent face)

A `SKILL.md` instructing the agent to call `y402 pay --unattended <URL>` when it
encounters a paywalled / `402` endpoint, and to surface the returned body. The skill
carries no logic of its own — all custody, policy, and protocol handling live in the
CLI/core.

## Configuration & file layout

- Config directory: `~/.config/y402/` (XDG).
  - `config.toml` — caps, default network, RPC URLs, keystore backend hint.
  - `audit.jsonl` — append-only payment log.
  - encrypted keystore file (only when the keyring fallback is in use).
- Key material in the OS keyring on the happy path; otherwise the encrypted file.

## Dependencies

- `x402` — protocol layer (payload/typed-data construction). Local code, not a
  middleman; no client-side facilitator configured.
- `eth-account` — wallet, key management, EIP-712 / EIP-3009 signing (the trust root).
- `keyring` — OS keyring access with fallback.
- `qrcode` — terminal QR for `topup`.
- `httpx` — HTTP client for the x402 exchange.
- `typer` — CLI.
- `tomlkit` — config read/write.
- (later) `mcp` — MCP server wrapper.

Tooling: `uv` for environment/deps, `pytest` for tests.

## Testing strategy (TDD)

- **Unit:** policy engine (thresholds, caps, daily rollover); network selection from
  sample `accepts[]`; config round-trip; keystore backend selection (mocked keyring,
  forced-fallback path); EIP-3009 typed-data assembly + signature verification with a
  known test key.
- **Integration:** Base Sepolia faucet USDC against a local mock resource-server +
  mock settler, plus one real testnet endpoint smoke test of the full `pay` path.

## v1 scope vs later

- **v1:** `wallet`, `keystore`, `registry`, `x402` pay path, `policy` + caps + audit,
  the six CLI commands, the Claude skill, Base Sepolia (registry ready for mainnet),
  gasless local-signing settlement, single EVM key.
- **Later:** MCP wrapper, Solana / non-EVM backend, headless key hardening,
  multi-account, broader wallet operations. (Self-settle/ETH is **out of scope**, not
  merely deferred.)
